# Test Plan — Yandex Disk REST API

## Цель

Проверить основные операции REST API Яндекс.Диска для работы с папками и автоматизировать основные позитивные и негативные сценарии.

## Стек

- Python 3
- Pytest
- requests

## Проверяемые методы

- PUT — создание папки
- GET — получение информации о ресурсе
- POST — копирование ресурса
- DELETE — удаление ресурса

## Автоматизированные сценарии

### PUT /v1/disk/resources

- PUT-01: создание папки с валидным `path` — ожидается `201 Created`
- PUT-02: запрос без обязательного `path` — ожидается `400 Bad Request`
- PUT-03: создание уже существующей папки — ожидается `409 Conflict`

После успешного создания дополнительно проверяется наличие папки через GET.

### GET /v1/disk/resources

- GET-01: получение существующей папки — ожидается `200 OK`
- GET-02: получение ресурса с параметром `fields` — ожидается `200 OK`
- GET-03: запрос без обязательного `path` — ожидается `400 Bad Request`
- GET-04: получение несуществующего ресурса — ожидается `404 Not Found`
- GET-05: запрос без OAuth-токена — ожидается `401 Unauthorized`

Для существующего ресурса проверяются основные поля ответа: `name`, `type` и `path`.

### POST /v1/disk/resources/copy

- POST-01: копирование существующей папки — ожидается `201 Created` или `202 Accepted`
- POST-02: копирование несуществующего ресурса — ожидается `404 Not Found`
- POST-03: копирование в уже существующий `path` без `overwrite` — ожидается `409 Conflict`
- POST-04: копирование с `force_async=true` — ожидается `202 Accepted`

После успешного копирования наличие созданной копии проверяется через GET.

Для асинхронного копирования выполняется проверка состояния операции до её завершения.

### DELETE /v1/disk/resources

- DELETE-01: удаление существующей папки с `permanently=true` — ожидается `204 No Content` или `202 Accepted`
- DELETE-02: удаление несуществующего ресурса — ожидается `404 Not Found`

После успешного удаления выполняется GET-запрос и проверяется, что ресурс больше не существует.

## Работа с асинхронными операциями

Для сценария с `force_async=true` API может вернуть `202 Accepted` и ссылку `href` на созданную операцию.

Тест выполняет polling этой операции:

1. получает состояние операции по `href`;
2. если статус `in-progress`, повторяет запрос через небольшой интервал;
3. при статусе `success` продолжает проверку результата;
4. при статусе `failed` тест завершается с ошибкой;
5. ожидание ограничено timeout, чтобы тест не выполнялся бесконечно.

## Работа с тестовыми данными

Для тестов создаются уникальные имена папок с использованием UUID.

Это позволяет:

- запускать тесты повторно;
- уменьшить вероятность конфликта между тестовыми ресурсами;
- не зависеть от данных предыдущего запуска.

Подготовленные тестами ресурсы удаляются после выполнения тестов.

## Дополнительные сценарии для дальнейшего покрытия

Следующие сценарии были рассмотрены при составлении тест-плана, но не входят в текущий набор автоматизированных тестов:

### PUT

- создание папки внутри несуществующего родительского каталога

### POST

- запрос без параметра `from`
- запрос без параметра `path`
- копирование с `overwrite=true`
- запрос без OAuth-токена

### DELETE

- обычное удаление ресурса с перемещением в Корзину
- проверка наличия удалённого ресурса в Корзине
- восстановление ресурса из Корзины
- запрос без параметра `path`
- запрос без OAuth-токена
- удаление с `force_async=true`

### Связанные сценарии

- полный жизненный цикл ресурса: создать → получить → скопировать → удалить
- удаление → проверка Корзины → восстановление

## Вне текущего scope

Специально не воспроизводятся ошибки, которые зависят от тарифа, состояния сервиса, ограничений аккаунта или инфраструктуры, например:

- `403 Forbidden`
- `406 Not Acceptable`
- `412 Precondition Failed`
- `413 Payload Too Large`
- `423 Locked`
- `429 Too Many Requests`
- `503 Service Unavailable`

Цель проекта — проверить основные операции API и наиболее реалистичные позитивные и негативные сценарии, а не искусственно воспроизводить все возможные HTTP-ошибки.
